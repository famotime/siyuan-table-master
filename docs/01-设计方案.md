# 思源笔记高级表格插件 - 设计方案

- 文档版本：v1.0
- 创建日期：2026-06-20
- 目标思源版本：SiYuan `v3.5.7` / petal `v1.1.8`
- 参考项目：[tgrosinger/advanced-tables-obsidian](https://github.com/tgrosinger/advanced-tables-obsidian) + 核心库 [@tgrosinger/md-advanced-tables](https://github.com/tgrosinger/md-advanced-tables)
- 稳定性：设计稿（待评审）

---

## 0. TL;DR（执行摘要）

本方案设计一款思源笔记插件 `siyuan-advanced-tables`，复用 Obsidian 生态成熟的核心库 `@tgrosinger/md-advanced-tables`（MIT 协议，与编辑器解耦），为思源原生 **`NodeTable` 表格块**提供增强编辑能力，包括：自动格式化、Tab/Enter 导航、行列增删移动、排序、对齐、转置、电子表格公式、CSV 导出等。

**核心技术结论**：思源表格块的存储本质是 GFM 风格的 Markdown 纯文本（通过 Lute 与 DOM 双向转换），与 `md-advanced-tables` 库的输入输出模型天然契合。关键适配工作集中在两点：

1. 实现 `ITextEditor` 适配器，把"行/选区"语义映射到思源的 Protyle 编辑器（`getRange` / `updateTransactionElement` / `getBlockKramdown`）；
2. 通过 `keydown` 拦截 + 块级 DOM 操作，绕开 Obsidian 依赖的 CodeMirror 扩展机制（思源无 CM6 编辑器扩展点）。

**可行性评级：高**。所有依赖的 API 均为 stable，不存在公开 API 不可达的硬阻断。公式、CSV 导出等高级功能可随核心库直接获得。主要风险在于 Protyle 的 DOM→Markdown 还原精度与选区定位（详见第 7 节风险）。

### 1.3 适配层契约（ITextEditor 接口）

`obsidian-text-editor.ts` 仅实现以下方法，核心库据此完成所有操作：

```ts
interface ITextEditor {
  getCursorPosition(): Point;          // 当前行、列
  setCursorPosition(pos: Point): void;
  setSelectionRange(range: Range): void;
  getLastRow(): number;
  acceptsTableEdit(row: number): bool; // 该行是否属于表格（排除代码/数学块）
  getLine(row: number): string;
  insertLine(row: number, line: string): void;
  deleteLine(row: number): void;
  replaceLines(startRow, endRow, lines: string[]): void;
  transact(func: () => void): void;    // 事务包装（用于 undo）
}
```

**关键洞察**：该接口的抽象粒度是"行（row）+ 字符位置（column）"，对应 Markdown 源码视图。Obsidian 因为有 CodeMirror，天然是行式纯文本编辑器。**思源的挑战正是此处**——思源是 WYSIWYG 块编辑器，没有暴露"第 N 行文本"的接口，需要我们自己构造。

### 1.4 核心库的输入输出模型

- 输入：当前光标位置 + 文档文本（按行）。
- 处理：识别光标所在的表格范围（连续的 `|...|` 行），解析为矩阵，执行操作。
- 输出：调用 `replaceLines` 覆盖该范围、`setCursorPosition` 移动光标。
- **不依赖任何编辑器实例，纯函数式 + 回调** → 这是可移植性的根本保证。

## 2. 思源笔记能力评估

### 2.1 表格块的本质：GFM Markdown 纯文本

| 维度 | 结论 | 证据 |
|---|---|---|
| 块类型 | `NodeTable` / DB `type='t'`，叶子块 | `developer_docs/05-block-model/块类型详表-Node与DB映射.md` |
| 单元格内容 | **纯文本 + 行内元素**（粗体/链接等），**不支持块级嵌套** | 官方 issue [#14118](https://github.com/siyuan-note/siyuan/issues/14118)（已关闭） |
| 设计哲学 | 为保证 Markdown 导出迁移性，刻意保持表格简单 | 同上 issue 官方回复 |
| 底层存储 | GFM 风格 `| col \| col |` 表格 Markdown | Lute 渲染器双向转换 |
| API 读写 | `getBlockKramdown(id)` 取源码、`updateBlock` 写回 | `developer_docs/03-kernel-api/常用接口调用示例.md` |

**这条结论至关重要**：思源表格 = 一段 GFM Markdown 文本 + 一个块 ID。这与 `md-advanced-tables` 库"操作纯文本表格"的模型完全一致，移植的语义摩擦极小。

### 2.2 编辑器（Protyle）操作能力（来自 petal 类型定义）

通过 `getActiveEditor()` / `getAllEditor()` 获取 `Protyle` 实例，关键可用方法：

| 方法 | 用途 | 适配 ITextEditor 的作用 |
|---|---|---|
| `protyle.wysiwyg.element` | WYSIWYG 根 DOM | 定位表格块 DOM 节点 |
| `protyle.getRange(element)` | 获取当前选区（`Range`） | 读取光标所在单元格、列 |
| `protyle.hasClosestBlock(node)` | 向上找最近的块 | 定位 `NodeTable` 容器 |
| `protyle.updateTransactionElement(el, oldHTML)` | **更新块 DOM 并入事务**（含 undo） | 写回格式化后的表格 |
| `protyle.transaction(doOps, undoOps)` | 原生事务（基于 `IOperation`） | 备选写入路径 |
| `protyle.lute` | Lute 实例，提供 `HTML2Md` / `BlockDOM2HTML` | **DOM ↔ Markdown 双向转换** |
| `protyle.focusBlock(el)` | 聚焦块 | 操作后恢复光标 |

### 2.3 平台约束

- 事件总线：`click-editorcontent`、`switch-protyle`、`loaded-protyle-*` 均可用于感知编辑器状态（`developer_docs/02-plugin-api/事件总线事件清单与版本差异.md`）。
- 快捷键：思源 `addCommand` 支持 `hotkey` 声明（petal v1.1.8 放宽约束），**但思源没有 CM6 的 keymap 扩展点**，Tab/Enter 拦截需通过 DOM `keydown` 监听实现（见 3.3）。
- 移动端：`mobile-keyboard-show/hide` 可用于功能降级。

### 2.4 与 Obsidian 的关键差异（移植风险点）

| 维度 | Obsidian | 思源 | 移植影响 |
|---|---|---|---|
| 编辑器模型 | CodeMirror，行式纯文本 | Protyle，WYSIWYG 块 + DOM | **需自建"行模型"适配层** |
| 表格光标定位 | `editor.getCursor()` 直接给行列 | 需从 DOM `Range` 反推单元格坐标 | 中等复杂度 |
| 文本读写 | `editor.replaceRange` | `getBlockKramdown` + `updateTransactionElement` | 异步化 |
| 键盘拦截 | `registerEditorExtension(keymap)` | 无等价扩展点，用 `keydown` | 需处理事件冒泡与默认行为 |
| 元数据校验 | `metadataCache.sections` | 通过块 DOM `data-type` 判断 | 简化 |
| 同步性 | 全同步 | 内核 API 异步 | 适配层需 async/事务封装 |

### 3.3 键盘拦截方案（思源特有）

由于思源无 CM6 keymap 扩展点，采用 **DOM 事件冒泡拦截**：

```ts
// src/keybind.ts 伪代码
wysiwyg.addEventListener('keydown', (e: KeyboardEvent) => {
  if (!settings.bindTab && e.key === 'Tab') return;
  const te = getCurrentTableEditor();      // 仅当光标在表格内
  if (!te?.cursorIsInTable()) return;
  if (e.key === 'Tab' && !e.shiftKey) { e.preventDefault(); te.nextCell(); }
  else if (e.key === 'Tab' && e.shiftKey) { e.preventDefault(); te.previousCell(); }
  else if (e.key === 'Enter' && settings.bindEnter) { e.preventDefault(); te.nextRow(); }
}, true);  // 捕获阶段优先于思源默认处理
```

注意点：
- 用捕获阶段（`true`）确保在思源原生 Enter（换行/创建块）之前拦截。
- 仅当 `cursorIsInTable()` 为真时阻止默认行为，不影响表格外的编辑。
- CJK 输入法（中文/日文）场景下需检查 `e.isComposing`，避免吞输入法确认键。

### 3.4 行模型适配（核心难点解法）

核心库期望"第 N 行文本"的行式视图，思源给出的是 DOM。适配方案：

1. **读取**：光标定位到表格块 DOM → 取 `data-node-id` → `fetchSyncPost('/api/block/getBlockKramdown', {id})` 得到表格 Markdown 文本 → 按行拆分。
2. **核心库操作**：在行数组上跑 `TableEditor`，得到新行数组 + 目标光标（行号、列号）。
3. **写回**：把新行数组重新拼成表格 Markdown → 通过 `protyle.lute.Md2HTML` 转 DOM（或直接用 `updateBlock` 内核 API 以 markdown 数据类型更新）→ `updateTransactionElement` 入事务。
4. **光标恢复**：把目标行列号反向映射回 DOM 单元格，用 `protyle.getRange` + Selection 重新定位。

> 注：思源 kramdown 输出对表格会输出标准 `| |` 格式，`md-advanced-tables` 库能正确解析。需在适配层单测验证 kramdown ↔ GFM 的往返一致性。

## 5. 适配层关键接口设计

### 5.1 SiyuanTextEditor（实现 ITextEditor）

```ts
export class SiyuanTextEditor {
  constructor(
    private protyle: Protyle,
    private tableBlockEl: HTMLElement,   // NodeTable 的块根 DOM
    private blockId: string,
  ) {}

  // —— 读 ——
  async getCursorPosition(): Promise<Point> { /* DOM Range → 行列 */ }
  async getLastRow(): Promise<number>      { /* kramdown 行数 - 1 */ }
  async acceptsTableEdit(row): Promise<boolean> { /* 始终 true，已限定在表格块内 */ }
  async getLine(row): Promise<string>      { /* 缓存的 kramdown 第 row 行 */ }

  // —— 写 ——
  async setCursorPosition(pos): Promise<void> { /* 行列 → DOM Range */ }
  async setSelectionRange(range): Promise<void> { /* 同上 */ }
  async insertLine(row, line): Promise<void>   { /* 改写缓存，标记 dirty */ }
  async deleteLine(row): Promise<void>         { /* 同上 */ }
  async replaceLines(start, end, lines): Promise<void> { /* 同上 */ }

  // —— 事务 ——
  async transact(fn): Promise<void> {
    // 预读 kramdown → 执行 fn（操作内存行模型）→ flush 写回块
    await this.reload();           // 读最新 kramdown 到内存
    await fn();
    await this.flush();            // 合并写回 + updateTransactionElement
  }
}
```

> **设计要点**：核心库原本假设同步 `transact`，思源是异步 IO。方案是在 `transact` 入口预读一次 kramdown 到内存行模型，所有 `getLine/replaceLines` 操作内存，`transact` 结束统一 flush。这样核心库代码无需改动，适配层吸收异步性。

## 6. 数据流与生命周期

### 6.1 单次操作数据流（以"插入列"为例）

```
用户点"插入列"命令
   │
   ▼
命令分发：取当前 Protyle + 光标所在表格块 DOM
   │
   ▼
new SiyuanTextEditor(protyle, tableEl, blockId)
   │
   ▼
new TableEditor(ctx)  →  内部 new MTEEditor(ctx)
   │
   ▼
tableEditor.insertColumn()
   │
   ▼
mte.insertColumn(opts)
   │  ┌─ transact(async () => {
   │  │    ctx.reload()              // 读 kramdown → 行模型
   │  │    解析表格 → 在当前列右插空列 → 重排对齐 → 重新格式化
   │  │    ctx.replaceLines(...)     // 写内存
   │  │  })()
   │  └─ ctx.flush()                // 行模型 → markdown → updateBlock → updateTransactionElement
   ▼
DOM 更新 + undo 栈入栈 + 光标移到新列
```

### 6.2 插件生命周期

```
onload():
  - loadData() 加载设置
  - 注册命令（addCommand × 20+）
  - addTopBar（顶栏按钮，打开 Dock）
  - addDock（表格工具栏侧栏）
  - eventBus.on('switch-protyle', 安装 keydown 监听到新编辑器)
  - eventBus.on('loaded-protyle-static/dynamic', 同上)

onunload():
  - 移除所有 keydown 监听
  - eventBus.off(...) 成对解绑
```

## 7. 风险评估与缓解

| 风险 | 等级 | 说明 | 缓解 |
|---|---|---|---|
| kramdown 与 GFM 表格格式往返失真 | 高 | 核心库按 GFM 解析，思源 kramdown 可能有 `{: id=...}` 尾部 IAL | 单测覆盖；flush 时只替换表格主体行，保留块 IAL |
| DOM Range ↔ 行列号映射不准 | 高 | 单元格内含多行内联元素时光标列号难算 | 用 `getLine` 文本长度而非 DOM 偏移做列计算 |
| Tab/Enter 拦截影响非表格区或输入法 | 中 | 捕获阶段 preventDefault 过于激进 | 严格 `cursorIsInTable()` 前置判断 + `isComposing` 检查 |
| 写回块后 Protyle 重新渲染丢失光标 | 中 | `updateTransactionElement` 触发重渲染 | 操作完成后主动 `focusBlock` + 重新 setRange |
| `getBlockKramdown` 异步导致快速连击竞态 | 中 | 用户连续按 Tab | 适配层加操作锁（`Promise` 链串行化） |
| 核心库版本升级 API 变更 | 低 | npm 依赖 | 锁定版本，pin 在验证过的 minor |
| 移动端键盘拦截失效 | 低 | M1 不支持移动端 | 设置项标注，后续迭代 |

1. **块级写入路径选型**：优先 `protyle.updateTransactionElement`（带 undo、DOM 直更）还是 `/api/block/updateBlock`（走内核、跨端一致但无前端 undo）？倾向前者，需原型验证。
2. **光标列号计算**：基于 Lute 还原的纯文本列还是 DOM 文本偏移？倾向前者（与核心库一致）。
3. **公式功能**：核心库公式行紧跟表格，思源表格块后的"行"是独立块，公式行如何承载？需设计为表格块**内部**的尾部 markdown 行（kramdown 允许）。
4. **插件名与仓库**：建议 `siyuan-advanced-tables`（与本地目录一致，便于集市上架）。
