## 决策 1：块级写入路径选型

**问题**：更新表格块内容时，选择 `protyle.updateTransactionElement` 还是 `/api/block/updateBlock`？

| 选项 | 优势 | 劣势 |
|---|---|---|
| A. `updateTransactionElement` | 前端 undo 可用；DOM 直更 | 需要精确的 oldHTML；重渲染时机不确定 |
| B. `/api/block/updateBlock` | 跨端一致；markdown 数据类型直接写入 | 无前端 undo（需自行管理）；异步网络请求 |

**决策**：**选 B — `/api/block/updateBlock`（markdown 数据类型）**

**理由**：
1. 思源 Protyle 的 `updateTransactionElement` 需要提供精确的 `oldHTML`，对表格这种结构复杂的 DOM 元素很难保证旧 HTML 完全匹配，易导致渲染异常。
2. `/api/block/updateBlock` 直接以 markdown 写入，内核负责 Lute 渲染，结果更可靠。
3. undo 虽然不是自动的，但可以在适配层手动实现（存 oldKramdown → flush 时注册 undo 操作）。
4. 异步性已被适配层的 `reload → 内存操作 → flush` 策略吸收。

**风险缓解**：M1 阶段补充手动 undo 实现。

## 决策 2：光标列号计算方法

**问题**：核心库的 `Point.column` 是纯文本字符偏移，思源 DOM 给出的是 Selection Range。如何映射？

| 选项 | 优势 | 劣势 |
|---|---|---|
| A. 基于 DOM 文本偏移 | 精确（ContentEditable 选区） | 需遍历 DOM 子树计算偏移；内联标记（粗体/链接）增加复杂度 |
| B. 基于 kramdown 纯文本偏移 | 与核心库一致；实现简单 | DOM→文本偏移反推不够精确（内联标记长度不同） |

**决策**：**选 B — 基于 kramdown 纯文本偏移（近似映射）**

**理由**：
1. 核心库所有操作的输入输出都是纯文本行列坐标，与其保持一致可避免双重转换。
2. 内联标记（如 `**bold**`）在 DOM 中是标签嵌套，在文本中是标记字符，精确映射复杂度极高，投入不值得。
3. 近似映射在大多数场景下够用：光标定位到单元格起始位置即可，不需要精确定到某个字符。
4. 操作后恢复光标时，通过 DOM 单元格坐标反向映射，只需要定位到 `<td>` / `<th>` 元素内部起始即可。

**风险缓解**：适配层的 `cellCoordToRange` 提供了 `toStart` 参数，默认定位到单元格起始而非精确字符。后续可按需增加精度。

## 决策 3：公式承载方式

**问题**：核心库的公式行紧跟在表格行之后（同一文本块内），思源的块是独立的内容单元，公式行如何承载？

| 选项 | 优势 | 劣势 |
|---|---|---|
| A. 公式行作为表格块内部 markdown 尾部行 | 与核心库兼容；无需额外存储 | `getBlockKramdown` 输出中公式行可能被 IAL 行分隔 |
| B. 公式存储在块属性 `custom-formulas` | 不干扰 kramdown 结构 | 核心库无法直接读取；需属性→行转换 |
| C. 使用 HTML 注释 `<!-- ... -->` 承载公式 | kramdown 输出保留；核心库原生支持 | 可读性差 |

**决策**：**选 A — 公式行作为表格块内部 markdown 尾部行**

**理由**：
1. kramdown 往返测试（M0.3）验证：`getBlockKramdown` 输出的表格行按行解析，公式行（以 `<!--` 或 `|` 开头的特殊行）在表格行范围内。
2. `parseTableKramdown` 已正确分离表格行和 IAL 行，公式行自然落在表格行范围内。
3. 核心库的 `_createIsTableFormulaRegex` 能正确识别公式行，无需修改。
4. `updateBlock` 以 markdown 写入时，公式行随表格内容一起保留。

**风险缓解**：M2 阶段用真实思源环境验证公式行的 kramdown 往返。

## 决策 4：CJK 全角字符对齐策略（新增决策项）

**问题**：核心库 `FormatType.NORMAL` 把 CJK 字符按 1 字符宽度计算 padding，但显示时 CJK 占 2 宽度，导致列宽不对齐。

| 选项 | 优势 | 劣势 |
|---|---|---|
| A. 默认使用 `FormatType.WEAK`（无 padding） | 最简单；无对齐问题；思源渲染表格时自动对齐 | 源码表格不整齐（可读性略差） |
| B. 使用 `FormatType.NORMAL` + 适配层 CJK 校正 | 源码整齐 | 校正逻辑复杂；需重建所有行 |

**决策**：**默认 WEAK + 可选 NORMAL + CJK 校正**

**理由**：
1. 思源编辑器是 WYSIWYG，表格渲染自动对齐，源码是否整齐不是核心需求。
2. WEAK 格式最安全，不做 padding 就没有 CJK 对齐问题。
3. 提供 `fixCJKWidth` 设置项，用户选择 NORMAL 时由适配层 `fixCJKSeparatorWidth` 做后处理校正。
4. 校正逻辑已在 `table-model.ts` 中实现并通过单测。

**默认值**：`formatType: FormatType.WEAK`, `fixCJKWidth: true`
